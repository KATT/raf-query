# Core behaviors: where each one lives

Each opt-in behavior or distinct mechanism of `@raf-query/core` has a folder in `packages/core/src` with its implementation and a test whose header explains how it works inside ([decisions/core-behavior-folders.md](./decisions/core-behavior-folders.md)). Read the test header first, then the code.

| Behavior                  | Code                                              | Test                                          | How it works                                                                                                                                                                                                                                        |
| ------------------------- | ------------------------------------------------- | --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `retry()`                 | `links/retry/retry.ts`                            | `retry.test.ts`                               | A part with a link: loops around `next(op)`, waiting on the client's `Clock` (and for `online` when offline) between attempts; the `retry` option overrides the attempts; never retries a thrown `Response`, an aborted request or a server client. |
| `timeout(ms)`             | `links/timeout/timeout.ts`                        | `timeout.test.ts`                             | A part with a link: calls `next(op)` with a signal it aborts with a `QueryTimeoutError` after `ms` on the `Clock`, and rejects with it.                                                                                                             |
| `focusRefetch()`          | `features/focus-refetch/focus-refetch.ts`         | `focus-refetch.test.ts`                       | A feature (a part with `setup`): on `visibilitychange` / `focus` while visible, refetches read, stale entries unless `refetchOnWindowFocus` is `false`.                                                                                             |
| `reconnectRefetch()`      | `features/reconnect-refetch/reconnect-refetch.ts` | `reconnect-refetch.test.ts`                   | A feature: the same sweep on `online`, opted out by `refetchOnReconnect: false`. The sweep and `optionOf` (a query's option, else the client's default) are in `features/shared.ts`.                                                                |
| `polling()`               | `features/polling/polling.ts`                     | `polling.test.ts`                             | A feature: subscribes to client events and keeps a `Clock` timer per read entry with a positive `refetchInterval`; each tick starts the entry's request.                                                                                            |
| `recommended()`           | `presets.ts`                                      | `links/retry/retry.test.ts` ("recommended()") | Returns an array of parts, `retry()` and the three features, typed with the options they declare.                                                                                                                                                   |
| Hydration                 | `hydration/hydration.ts`                          | `hydration.test.ts`                           | `dehydrate` / `dehydrateStream` snapshot entries (pending ones as promises, thrown errors redacted); `hydrate` writes newer data by key and adopts a sender's pending request. Nothing in the kernel imports it.                                    |
| Paging                    | `infinite/infinite.ts`                            | `infinite.test.ts`                            | `infiniteQueryOptions` sets `~run`, which the entry calls instead of `queryFn`: loads pages from `initialPageParam`, or one page in `op.direction`, keeping `maxPages`.                                                                             |
| Structural sharing        | `structural-sharing/structural-sharing.ts`        | `structural-sharing.test.ts`                  | `write` passes new data through `replaceEqualDeep`, so equal parts keep their identity and equal data keeps its thenable; plain objects and dense arrays only, own keys only.                                                                       |
| Keys and groups           | `keys/keys.ts`                                    | `keys.test.ts`                                | Keys are plain arrays hashed with sorted fields; `group()` builds keys under a path and matches by prefix; a dev check rejects a subgroup and a query sharing a name.                                                                               |
| Targets                   | `keys/targets.ts`                                 | `targets.test.ts`                             | A verb turns each target into a stamp at the next `~seq`; an entry is invalidated while a matching stamp is newer than its data. Factories match by identity and partial input, groups by key prefix, `{ where }` by predicate.                     |
| Tags (a recipe, not core) | —                                                 | `keys/tags-recipe.test.ts`                    | A `part<Tags>()` that only declares a `tags` option, plus a `where` target over `query.options.tags`. See [decisions/tags-userland.md](./decisions/tags-userland.md).                                                                               |
| Streams (kernel)          | `entry.ts` (`pump`)                               | `streams.test.ts`                             | An async-iterable result with `stream: { initial, reduce }` is folded chunk by chunk; the request settles at the first chunk.                                                                                                                       |

What a part is, and how a client's parts type its queries' options and `queryFn` context, is in [decisions/parts-options-context.md](./decisions/parts-options-context.md): `part()` and `createQueryClient` in `client.ts`, the root types in `root.ts`, tests in `client.test.ts` ("a client's parts") and `types.test-d.ts` ("root types").

The kernel (`client.ts`, `entry.ts`, `load.ts`, `verbs.ts`, `options.ts`, `root.ts`, `thenable.ts`, `subscribe.ts`) stays flat, with its tests beside it: `load.test.ts`, `reading.test.ts` (reads, gc, reset), `verbs.test.ts`, `client.test.ts`, `server.test.ts`, `races.test.ts`, and the type tests `types.test-d.ts` and `extension.test-d.ts`.
