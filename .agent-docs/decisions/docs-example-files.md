# Docs samples import real libraries; integration pages are example apps (human)

- **Samples import real libraries and real app code, never stubs of them** (human): `@tanstack/react-router`, `next`, `effect` and so on, and app code a sample leans on (`api.ts`, `queries.ts`) is a real file. Incidental clients a page only names in passing (axios) are a hidden `declare`, not a dependency.
- **Only pages that walk through an app's files get an example app** (human: "maintainability and easy to grok examples"): `www/content/<page>/` for `quick-start`, `tanstack-start` and `nextjs`, whose samples are files a reader copies. One app per guide (33 apps, 18 route trees, a dependency per one-off library) was more to maintain than the samples it compiled.
- **Every other sample is an inline fence written against one shared app, `www/content/_shared/`** (agent): its hidden setup imports `~/api.ts` and `~/queries.ts`, and may `declare` the page's own leaf components and values (`Spinner`, `slug`), never a library's API. Leaf components stay per page: their props differ from page to page. A fence that defines a route starts with `// @filename: _shared/src/routes/<route>.tsx` and compiles as that file, because `Route.useLoaderData()` reads its type from the registered route tree, which would otherwise see the shared app's empty placeholder route.
- **Each app is its own TypeScript project** (agent): `content/<page>/tsconfig.json` extends `content/tsconfig.base.json`. Route trees `declare module "@tanstack/react-router"` globally, so two apps in one program would clash. `pnpm --filter @raf-query/www typecheck` runs `tsc -p` per app (`build/typecheck-examples.ts`). Lost: `tsc -b`, which writes `tsbuildinfo` files into `content/`.
- **Route trees are generated** (agent): `build/example-apps.ts` runs `@tanstack/router-generator` for each app with `src/routes` at build start, like TanStack Start's plugin. `src/routeTree.gen.ts` is committed so the editor and `tsc` work without a build.
- **`<<< ./page/src/file.tsx#name` in a page** (agent; VitePress's syntax): `build/snippets.ts` expands it into a `twoslash` block, so the HTML and the agent markdown both see a normal fence. `#name` shows every `// #region name` … `// #endregion` part of the file (VS Code markers); without `#name`, the whole file. `[title]` overrides the title (the path inside the app by default) and `[]` drops it.
- **The whole file compiles, only the region shows** (agent; like mdBook's `rustdoc_include`): the other lines go between `// ---cut-start---` and `// ---cut-end---`. Region-only includes (VitePress, Vocs, TypeDoc, remark-code-import) compile the region on its own and lose its imports.
- **A block compiles in its file's app** (agent): the closest folder with a `tsconfig.json` (`appOf` in `build/example-apps.ts`). The expansion writes the block's `// @filename` from the content dir, and `build/markdown.ts`'s Twoslash function picks the app from it, reads the app's `tsconfig.json` and hands Twoslash every file in it as `extraFiles`, so a block's program has what `tsc` has (the route tree, which nothing imports). Each block compiles as `<file>.<region>.twoslash.<ext>` next to the file, since Twoslash empties a block's files once it's done.
- **The build logic is Effect** (human): `www/build` reads files and runs commands through `FileSystem`, `Path` and `ChildProcessSpawner`, never `node:fs` / `node:child_process`. Vite's hooks and `vite.config.ts` are the edge that runs it with `NodeServices.layer`, and failures are `ContentError`s naming the file. Each render reloads the apps its blocks use, so an edit to an app file shows up in dev. TypeScript still reads `tsconfig.json` through `ts.sys`, because it resolves `extends` and `include` itself.
- **Example files are linted** with `.oxlintrc.json` relaxing the rules that fight readable samples (key order, `curly`, type assertions, button `type`).
