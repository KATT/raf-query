# Examples fetch through a shared REST API (human asked, agent designed)

- Human: the Next.js examples' server actions run one at a time ("can they be called in parallel?"), so expose a RESTful API every app supports, with types from `@examples/db` inferred the whole way.
- **Why not server actions**: Next.js's client sends a page's server actions through the router's single action queue (`app-router-instance.js`: `actionQueue.pending` / `.next`), so invalidation refetches and "load more" wait behind each other and behind mutations. Next's own docs say not to fetch with them. Measured in the browser: each action `POST` starts when the previous one ends.
- **`examples/.shared/api`** (`@examples/api`): a [Hono](https://hono.dev) app (`app.ts`) over `@examples/db`. Inputs are validated with `@hono/standard-validator` and the db's Zod schemas; path and query strings are coerced (`z.coerce.number<string>()`) and then piped into db schemas such as `Cursor` / `IssueId`. Responses are whatever the db functions return, so `hc<Api>` infers them; 404 for a missing issue. `Api` is the type of the routes without the `/api` prefix, so the client reads `api.issues[":id"].comments.$get(...)`.
- **One client, two transports**, picked by the `./client` export conditions: `browser` → `browser.ts` (`fetch` to `/api`), `default` → `in-process.ts` (`app.request`, no network). Server components, Start's SSR loaders and Next's client-component SSR get the in-process one. An HTTP call to the server's own origin during SSR would need the origin and a second connection per render. No db or Hono app code reaches either framework's client bundle (checked, `next dev --webpack` included).
- `parseResponse` (Hono's: throws `DetailedError` when not ok) for reads and mutations; `parseFound` resolves `null` on 404: each app's issue query resolves `null`, and the page calls its framework's `notFound()` when it reads that.
- Mounted at `src/app/api/[...path]/route.ts` (Next), the server route `src/routes/api.$.ts` (Start) and the resource route `app/routes/api.$.ts` (React Router), handling `GET` / `PATCH` / `POST`.
- `infiniteQueryOptions` calls put `queryFn` first, in its own comment-separated sort partition: TypeScript infers the page type left to right, so a sorted `getNextPageParam` would see `unknown`. The callback params stay unannotated (`workspace/infer-callback-params`).
- Lost: server functions / server actions per app (serial in Next), tRPC or oRPC (another concept for readers to learn; Hono is a plain REST app any client can call), a self-request over HTTP during SSR.
