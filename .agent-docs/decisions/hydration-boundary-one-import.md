# One HydrationBoundary import for RSC and React Router (human asked)

Human: "make the hydration boundary the same import for rsc and react router … something in package.json that auto-picks the right file. If it adds payload or anything, don't do it."

- **`import { HydrationBoundary } from "@raf-query/react"`** everywhere. The main entry's `react-server` export condition points at `index-react-server.ts`, whose `HydrationBoundary` (`hydration-boundary-react-server.tsx`) is a server component that takes the request's `client` (dehydrating with the `sent` set) or a `state`. Everywhere else `index.ts` gives the `"use client"` one (`hydration-boundary.tsx`), which takes only `state`. Both entries re-export `index-shared.ts`, so the RSC graph never imports the client boundary (Next.js would make it a client reference).
- **One props type**, a union of `{ client, options?: DehydrateOptions }` and `{ state }`, declared in `hydration-boundary/hydration-boundary.tsx`. TypeScript can't see `react-server` (Next.js apps don't set `customConditions`), so both builds must type as the same component. The types can't catch `client` in a client component, so the client build throws "needs `state` here. `client` works only in server components." when `state` is missing (human: "the whole point is to make a simpler api, while still having it fool proof"). It costs a few bytes gzip in the client JS; without it, the misuse would crash inside `Hydrate` with a `TypeError`.
- **No payload:** Rolldown flattens `index-shared.ts` into `dist/index.mjs`, so the split entries cost `examples/nextjs` no client bytes and `examples/react-router` a few.
- Lost: a `@raf-query/react/react-router` subpath and a `/rsc` subpath for `HydrationBoundary` (there's no `/rsc`). Also lost: exact per-framework props types.
