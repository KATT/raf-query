# A partial input matches the input, not the key (human)

- `invalidateMany(qc, factory, partial)` and `[factory, partial]` in a target list (`invalidateMany`, `resetMany`, `removeMany`) match `partial` against the input the factory was called with: `PartialInput<F>` is `DeepPartial<InputOf<F>>`, and `matches()` runs `partialMatch(entry.input, stamp.partial)`.
- Why: matching the key's last segment made a partial's meaning depend on how the key was written. With `queryKey: posts("bySlug", input.slug)` the partial had to be `"hello"`, not `{ slug: "hello" }`. The input is what the app passes everywhere else (`invalidateOne`, `setData`, `load` entries), so the partial is part of that.
- A hydrated entry has no factory or input until it's read, so a factory target can't match it before then. Unchanged from key matching: `invalidateMany` covers it through its stamp, which is checked when `entryOf` links the entry to its factory on its first read; `resetMany` and `removeMany` act at once and skip it, while a group still reaches it by key. Documented in `keys.ts`'s header and `query-invalidation.md`.
- Lost: partials over keys that don't come from the input. A `where` target over `queryKey` covers those.
- Code: `PartialInput` in `packages/core/src/verbs.ts`, `matches` in `packages/core/src/keys.ts`. Tests: `verbs.test.ts` ("matches a partial against the input, whatever the key ends with", "matches a partial against a hydrated query once its factory reads it"), `types.test-d.ts` ("check inputs, partial inputs and tag parameters"). Docs: `www/content/query-invalidation.md#targets`.
