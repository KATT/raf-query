# Plugins, and builders that are always bound (human, 2026-11-11)

- **The name is "plugin"** (human: "part" was a bad name): `plugin()`, `Plugin<Decl>`, `createQueryClient({ plugins })`. A plugin has any of a link, a `setup` (a feature), a `context` for every `queryFn`, and it declares options ([parts-options-context.md](./parts-options-context.md)).
- **The default is a builder typed by the client factory** (human). So the packages export no `queryOptions` or `infiniteQueryOptions`: the only way to get a builder is to bind one ([bound-builders.md](./bound-builders.md)).
  - An app binds to its client factory, once, in its own `raf.ts`: `bindQueryOptions<typeof makeQueryClient>()`, `bindInfiniteQueryOptions<typeof makeQueryClient>()`, `bindUseQueryClient<typeof makeQueryClient>()`. Every factory imports the builders from that file. The quick start and every guide teach this path, starting with the client factory and `raf.ts`.
  - A library binds to the plugin declarations it needs: `bindQueryOptions<Convex & Optional<Retry>>()`.
  - `bindQueryOptions()` with no type argument is the any-client builder: the core's options only, and factories that run on any client. A package without requirements uses it. The docs mention it once, on the plugins page, and never as an app's default.
- **What follows for an app**: a bound factory runs only on a client that has its plugins. Components that call verbs get the client from the bound `useQueryClient`. Whatever carries the client between a loader and the framework is typed `ReturnType<typeof makeQueryClient>`, not the bare `QueryClient`: a TanStack Router context, a React Router context, Next's cached getter (inferred). A Next.js app makes its server client and its browser client with one function, so both have the same plugins. Tests give their client the app's plugins and turn behaviors off in `defaults`.
