# Experiment: typed error boundaries in `@raf-query/react` (human asked)

Option C of three competing takes on type-safe error boundaries for render-as-you-fetch on Effect and Effect RPC (A: a new library in `.experimental/effect-query`; B: on effect/reactivity atoms; C: this one, inside the existing packages). A generic failure (auth) is handled high in the tree and narrower ones further down; the compiler refuses a read that leaves a failure unhandled, and a read with nothing left returns plain data.

- **Where it lives:** `@raf-query/react/boundary` (subpath, not the main entry) plus a small core change. The demo is `.experimental/raf-query-boundaries/demo` (port 3012); the docs page is `www/content/typed-error-boundaries.md`, marked experimental.
- **Tuple API (human):** `const [App, useApp] = Boundary.root<R, U>(...)`, `const [X, useX] = Boundary.catchErrors(parent, { name, tags, fallback })`. Element 0 is the Provider, the parent of child boundaries and the argument of `Boundary.useRun(X)`. A hook or Provider with its parent's Provider missing above it throws a message naming both.
- **One read hook (human, shared with B):** `useX(factory, handle)` returns `A | Boundary.Unhandled<Left>`, which is `A` when nothing is left; `Boundary.isUnhandled` tells them apart. `Unhandled` holds `error` and `cause` and is cached per `Exit`, so a render sees the same object.
- **Tag-only errors (human):** the root declares every error as a type (`errors: Boundary.errors<U>()` or the second type argument; `Boundary.RpcErrors<typeof Group>` reads an RpcGroup). Boundaries list `_tag`s, checked against the universe (`AlreadyHandledAbove`, `TagSharedByMoreThanOneError`, typo via `Did you mean`, `CaughtAsAnotherType` on reads). The runtime matches `_tag` membership, so boundaries and components import errors with `import type` only. Trusting the tag is the cost: RPC errors are decoded, a hand-written Effect can lie with a cast.
- **Core keeps the Cause.** A failed first load's `Cause` is kept per rejected promise (`WeakMap`), and `exitThenable(promise)` reads it back as an `Exit`; a rejection with no Cause is a defect. Bindings route on that, not on the thrown value.

Agent decisions:

- **Reads take `(factory, handle)`** like every raf-query read, not a query value. Queries don't declare errors: the error type is the factory's Effect error.
- **Routing:** `Cause.findError`, then the innermost boundary on the read's chain that lists the failure's `_tag`. A typed failure no boundary lists comes back as an `Unhandled`, even where the types said nothing was left (a lying cast). Defects, interrupts and hydrated failures (no Cause crosses the wire) go to the root, whose fallback gets the `Cause`.
- **Promise `queryFn`s are untyped:** their error is `unknown`, so the read's type is plain data (`TypedErrorOf` maps `unknown` to `never`) and any failure goes to the root, even one with a listed `_tag`. Same rule as core's `throwsOnError` for untyped errors.
- **`Boundary.useRun(X)`, not `X.useRun()`:** a top-level hook that takes the Provider. React Compiler's lint rejects `useX.useY()`. `run(effect)` resolves with `A | Unhandled<Left>`; a caught failure goes to its boundary and the promise never settles. The Effect's services must come from the client (`QueryCache | R`).
- **Retry resets every failed, dataless, unobserved query in the boundary's client**, then renders again. React stops rendering siblings at the first throw, so a boundary can't know which other reads failed; resetting the unshown ones is what makes one click recover them all. A failure a component handled inline is observed, so a retry doesn't reload it.
- **Background refetch failures keep their data and don't route**; the demos reset the client on chaos changes instead of invalidating.
- **`useObservedQuery` is `"use no memo"`.** `www` compiles workspace-linked `packages/react/src` with React Compiler, which memoized the cache reads and froze results. The plain `useQuery` had the same latent bug.
- Type-error fixtures (`demo/type-errors/*.tsx`) are checked by `pnpm type-errors --check` against the generated `src/type-errors.gen.json`; knip treats them as entries.
- **The docs demo's type switches** (`www/src/demos/typed-error-boundaries/`): `www/build/type-controls.ts` writes the chain and component for each of the 24 switch configurations as virtual files next to the demo, compiles them in one TypeScript 6 language service (TS 7 has no JS API), and commits code, diagnostics and `^?` quick info to `type-controls.gen.json`. The browser runs no compiler. `--check` (in www `typecheck` and `build`) compares parsed JSON, so formatting doesn't make it stale; it also fails when a configuration compiles and `runnableChain` has no static chain for it, or the reverse. The app runs the four configurations that compile, and keeps the last one while the switches don't.
