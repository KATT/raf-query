# Examples on StackBlitz from a generated branch (human asked, agent designed)

- Human: "i want the examples deployed on stackblitz", like tRPC, which opens one folder of the repo as the project root and links it from each example's README.
- tRPC's examples only depend on published `@trpc/*` (written `npm:@trpc/x`, linked locally by `linkWorkspacePackages`), so `stackblitz.com/github/trpc/trpc/tree/main/examples/<x>` works from `main`. Ours also import the private `@examples/ui` / `@examples/db` from `examples/.shared/`, which a single folder doesn't contain. So `tooling/stackblitz` writes standalone copies, and `.github/workflows/stackblitz.yaml` pushes them to the `stackblitz` branch. Links point at `tree/stackblitz/examples/<app>`.
- Each copy is a pnpm workspace laid out like a typical one (human asked): the app in `apps/<app>`, `examples/.shared/*` copied as-is into `packages/`, a root `package.json` that runs the app's scripts. `@examples/*` stay `workspace:*`; `workspace:*` `@raf-query/*` become the version in `packages/*/package.json`. An earlier version used `file:` dependencies, which needed the shared packages' `devDependencies` stripped (npm installs a linked package's dev deps, adding a second React).
- The workflow runs on `workflow_run` of Release, not on push: after a release that version is on npm. The CDN serves npm's install metadata stale for a few minutes, so the sync polls it before installing. It installs and builds each copy with StackBlitz's built-in pnpm (8.15.6) and commits the lockfile; a copy that doesn't build never reaches the branch. Only the `main` apps are copied. The `.experimental/` ones depend on an unpublished package.
- The sync is an Effect program with tests (human asked: "If logic in ci getting complex, rewrite it in Effect").
- WebContainers limits, handled in the copies unless noted:
  - The `vp` CLI is native, so scripts use `vite` (the workspace overrides `vite` with Vite+, standalone gets plain Vite 8). Turbopack has no WebAssembly build, so dev is `next dev --webpack`.
  - AsyncLocalStorage loses its store across native `await` (stackblitz/webcontainer-core#1169), so Next.js ("Expected workStore to be initialized") and TanStack Start ("No Start context found") fail on their first request. It isn't StackBlitz's installer: installing with npm or pnpm gave the same errors. `webcontainer-async-context.mjs`, preloaded through `NODE_OPTIONS` in `.stackblitzrc`, makes `getStore()` fall back to the store last entered on that instance (as SvelteKit does). That is right while requests don't overlap, which holds for one person clicking around a demo. `async_hooks.AsyncLocalStorage` is a getter-only property, so it's replaced with `defineProperty`.
  - WebContainers' `Promise.resolve` returns anything `instanceof Promise` unchanged, including React Flight's decoded promises, whose `then` returns nothing. Core's `hydrateEntries` used to chain off `Promise.resolve(promise)`, so Next.js SSR entries resumed with `undefined` data. Fixed in core, which now adopts thenables through `new Promise` instead of relying on `Promise.resolve` semantics. To reproduce locally, run the copy with `--no-async-context-frame` plus preloads that drop promise context from AsyncLocalStorage and patch `Promise.resolve` that way.
  - `.stackblitzrc` sets `installDependencies: false` and `startCommand: "pnpm install && pnpm dev"`: StackBlitz's own installer doesn't read pnpm workspaces.
- Lost: separate `examples-*` repos per app (tRPC's `subtree.yml`; needs repos and deploy keys), making the apps self-contained on `main` (would undo the shared `examples/.shared/` packages, a human decision), and CodeSandbox, which TanStack links for Start instead (TanStack/router#7480).
