# `cancel` reverts and rejects its awaiters (agent)

- **`qc.cancel(factory, input)` / `qc.cancel(filter)`** and `QueryCache.cancel` / `Query.cancel` (agent, proposal for TanStack's `cancelQueries`), matched like `invalidate`. `Entry.cancel` (`entry.ts`) clears `inFlight`, reverts like the unobserved path (`revert`: `failureCountBefore`, not fetching; data, `updatedAt` and the promise untouched), fails the request's `Deferred` with `CancelledError` (Promise verbs: `AbortError`), then interrupts the request fiber it captured and waits for it (`Tasks.interrupt`), so the Promise resolves after an Effect `queryFn`'s finalizers. No `failed` event. Clearing `inFlight` first makes a response that races the interrupt a no-op in `settle`, so a `setData` right after `cancel` wins.
- **Awaiters fail, unlike TanStack** (which gives `fetchQuery` callers the cached data when there is some, as the unobserved path here does). An explicit cancel means the caller who asked for fresh data didn't get it; `fetch` resolving with stale data would hide that.
- **A first load stays pending**, like TanStack's revert (state back to pending, idle). `entry.pending` isn't rejected: a render suspended on it would hit an error boundary in the microtask before the `setData` that usually follows. The next `readUnsafe` / `prefetch` / `ensure` starts a request (`!hasData && !isFetching`) that settles the same promise, and `setData` resolves it. Lost: a suspended render with nothing reading again waits; TanStack's suspense re-renders on the rejected fetch promise and restarts. Same trade as [cancel-unread-requests.md](./cancel-unread-requests.md).
- Lost: `CancelOptions` (`silent`, `revert: false`). Only the revert behavior exists; `remove` drops data.
- Files: `packages/core/src/{entry,cache,query,client}.ts`, `www/content/query-cancellation.md#cancelling-yourself`, the `mutations.ts` sample (cancel before an optimistic `setData`).
