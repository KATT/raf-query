# Effect example app on TanStack Start and Effect RPC (human asked, agent designed)

- Human: an Effect-native example with Effect RPC, the same features as the other apps, on TanStack Router, deployed like the others. It's `examples/tanstack-start-effect` (port 3005, `pnpm dev:effect`); the other apps stay Effect-free.
- **TanStack Start**, not plain TanStack Router: same SSR, loaders and deploy as `examples/tanstack-start`, so the two diff cleanly (Promises vs Effect).
- **Effect RPC instead of the REST API**: `src/rpc.ts` is the contract (Effect Schemas, `Schema.TaggedError`s), `src/rpc-handlers.ts` implements it over `@examples/db` (server-only), `src/routes/rpc.ts` serves it. Each mutation is its own procedure declaring only the error it can raise (`UpdateTitle` → `EmptyTitle`, `UpdateBody` → `EmptyBody`, `SetStatus` → none), so `catchTags` is exhaustive per action. Effect's HTTP client posts to `<url>/` (it joins the base URL with an empty path), so requests are `POST /rpc/`.
- **In-process during SSR**: `#rpc-transport` (package `imports`, `browser` condition, like Next's `#latency-cookie`) gives the server a `fetch` that calls the RPC web handler directly, and the browser `/rpc`. That keeps `@examples/db` out of the client bundle. The in-process URL needs a host (`http://in-process/rpc`), since Effect's client resolves relative URLs against `location`.
- **`Issues` service** (`src/issues.ts`) is the group's `RpcClient`; the `QueryClient`'s `layer` provides it, so `queryFn`s, loaders and actions `yield* Issues`. Loaders and actions run with `queryClient.runPromise`; components read the typed client from the router context (`useQueryClient()` is `QueryClient<unknown>`).
- Lint: `workspace/infer-callback-params` is off for the app, because `Effect.fn` takes its parameter types from the generator.
- Lost: a separate Vite + TanStack Router SPA (no SSR, a different deploy); wrapping the shared Hono API in Effect `HttpApi` (keeps REST, but RPC is what was asked for).
