# `initialData` seeds new entries, and never crosses the wire (agent)

- **`initialData` / `initialDataUpdatedAt` are factory options** (`InitialDataField` in `options.ts`, on `QueryOptions` and `InfiniteQueryOptions`), not `QueryBehavior`: a default for every query makes no sense, so `config.defaults` doesn't take them. Typed `NoInfer<data>`: the `queryFn` alone infers the data type.
- **Seeded once, by the first factory call of an untouched entry** (`Entry.setOptions` → `seed`): no options attached before, `status: "pending"`, nothing in flight. So it never replaces fetched, written or hydrated data, nor a hydrated request or failure, as in TanStack (`getDefaultState` runs only when a `Query` is built). A function runs once per new entry. It goes in through `succeed`, so it's cached data: readers don't suspend, `ensure` resolves at once, `fetch` / `prefetch` follow `staleTime` from `initialDataUpdatedAt` (default: seeding time).
- **`undefined` is data** ([undefined-data.md](./undefined-data.md)): the check is `"initialData" in options`, so `initialData: undefined` seeds `undefined`. Cost: without `exactOptionalPropertyTypes`, TypeScript accepts `initialData: undefined` for any data type. A function that can return `undefined` is still a type error. Lost: TanStack's "`undefined` means none", which can't seed `undefined` data.
- **`reset` goes back to `initialData`**, seeded again (TanStack resets to its `#initialState`, which holds it). "Back to the state of a new entry" stays true.
- **Hydrated data always replaces initial data** (`Entry.isInitialData`, cleared by `succeed`): `takeNewer` ignores `updatedAt` against it, since the browser's seeding time is usually later than the server's fetch. A pending server query resumes into an entry that only has initial data instead of the browser fetching too.
- **Server caches use it** like any cached data, so they never fetch the query unless `invalidate` marked it ([server-verbs-no-revalidate.md](./server-verbs-no-revalidate.md)). **`dehydrateEntries` skips entries still holding it**, whatever the filter: the browser's call to the same factory seeds it, and a server copy that crossed would land as fetched data, so a later hydration of real data would be compared by `updatedAt` against a seed. Cost: `initialData` must be deterministic across server and browser, like a render. Lost: dehydrating it as TanStack does (its default filter sends `status: "success"`), which needs an "initial" marker on `DehydratedQuery`. A server entry whose initial data is replaced (invalidate, `setData`) is sent then: the stream's `updated` event reaches `dehydrateEntries` again.
- Tests: `client.test.ts`, `hydration.test.ts`, `infinite.test.ts` ("initialData" / "start from initialData's pages"), `use-query.test.tsx`, `ssr.test.tsx` ("initialData"). Docs: `www/content/caching.md#initial-data`.
