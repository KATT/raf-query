# Callable groups build flat keys (human picked, 2026-11-06)

- Human picked "tuple groups with flat keys", option A (a callable group): a group is a function. `group("posts")` and `group(posts, "drafts")` return one; `drafts("byId", input)` returns the plain array `["posts", "drafts", "byId", input]`.
- **Groups are the recommended way to build keys**, not the only one: `queryOptions` takes any plain array ([hand-written-keys.md](./hand-written-keys.md)). A group returns a `const`-inferred plain tuple, so a handle's `queryKey` (`KeyOf`) keeps its literal type and router serializers (React Router's loader-data types) keep it too.
- **A group matches as a prefix**: `path.every((segment, i) => key[i] === segment)`, so it reaches every subgroup and query below it, hydrated entries and hand-written keys included. Keys look the same in memory, on the wire, in devtools and to TanStack Query filters.
- **Nesting only as `group(parent, name)`**, never `group(posts("drafts"))`: the dev check needs the parent link.
- **Dev-only name check.** A subgroup and a query sharing a name under one parent would share a prefix, so invalidating the subgroup would reach the query. `group()` throws at whichever comes second (keys it builds only), behind `process.env.NODE_ENV !== "production"` (typed by a module-local `declare const process`), so production bundles drop it.
- Size (esbuild, `NODE_ENV=production`, gzip): `group()` 152 B alone, 62 B next to core; the dev check 0 B; core 48 B under matching object groups. `group()` lives in `keys.ts` on the main entry and tree-shakes away when an app doesn't call it.
- Lost: object groups (`{ group: "posts/drafts" }` as a key's first segment), and string keys in examples and docs.
- Code: `packages/core/src/keys.ts` (`group`, the check, `Group`, the matcher). Tests: `groups.test.ts` ("build flat keys…", "throw in development…", "skip the name check in production builds"), `verbs.test.ts` (group matching), `types.test-d.ts` ("keys"). Docs: `www/content/query-keys.md#groups`.
