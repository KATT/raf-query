# Requests keep writes made while they ran (agent)

- **Paged:** `fetchNextPage` / `fetchPreviousPage` add the loaded page to the entry's data as of when the page arrives (`latest(op, …)` in `infinite.ts`), not the data the request started with, so live caches (a subscription `setData`-ing loaded pages) keep those writes.
- If the write moved the end being loaded (its edge page param isn't deeply equal, by `hashKey`, to the one the request started from), the write wins and the loaded page is dropped: appending it would put a page after a list it doesn't follow.
- Full refetches keep, per page param, a page written after that page's read started (comparing the page `latest()` held when the read started with the one it holds at the end, by identity). A page written before its read started is read again, and the read wins. Why: the cache can't tell whether a write or a read is newer. A live writer, though, delivers every later change again, while a dropped write never comes back. So the write wins once the read is already under way. Without it, a live integration has to merge writes back itself, in a link.
- **Plain:** a request's answer is dropped when a `setData` landed after the request started (`entry.requestedAt > run.startedAt` in `fetchEntry`, `entry.ts`); the request still settles `ok`. Same reason. Streams and paged requests skip this rule: paged ones merge page by page, and every stream chunk is newer than the write it follows.
- Lost: replacing every page or the whole value (it silently reverts live writes), and a hook or an ordering guarantee for integrations to re-write after a request (every live integration would have to know about it).
- Tests: `packages/core/src/infinite/infinite.test.ts` ("writes while pages load"), `packages/core/src/verbs.test.ts` ("keeps data written while a request ran over the request's answer"). Docs: `infinite-queries.md#refetching`, `mutations.md#updates-from-mutation-responses`.
