# Only server-components-fed server renders skip unstarted queries; one provider everywhere (human)

- **Rule:** a server render leaves a query nothing started (no data, no error, no request in flight: a `waterfallHandle`'s query, one the cache dropped) to the browser only on clients fed by server components. Everywhere else it fetches during render. Why: only there does nothing carry a render's request to the browser and the RSC payload already holds what server components sent. Start streams the server cache (`dehydrateStream` in `setupRouterIntegration`), so a render-time fetch reaches the browser. React Router's loaders send `dehydrate()` snapshots, so a render-time fetch runs again in the browser: documented in `react-router.md` ("Queries no loader started") as the cost of starting a query outside a loader. A streaming React Router integration is the human's call, not built.
- **Marking:** the server components' `HydrationBoundary` (`hydration-boundary-react-server.tsx`) renders the client `Hydrate` with `fromServerComponents`. `Hydrate` calls `markFedByServerComponents(useQueryClient())` before its children render; it adds the client to a `WeakSet` in `browser-render.ts` only when `client.isServer`. The flag can't live in the RSC graph (different module instances), so it rides a serializable prop into the SSR graph. Edge, documented: a read that renders before the first boundary (a root layout's client component around `{children}`) fetches on the server, and the browser fetches it again.
- **Reads:** `startIfMissing` in `use-query.ts` doesn't start an idle entry on a marked client (no dev warning on any server client). `readOf` returns `browserRender(entry)` for any server client's entry still idle after that: marked clients' unstarted reads and disabled reads on every server client. It rejects with `BrowserRenderError`, digest `BAILOUT_TO_CLIENT_SIDE_RENDERING`, so Next.js reports nothing. The rejected thenable (not a throw from the hook) keeps the bail-out at the boundary above the `use()`.
- **No custom server entries.** Apps run each framework's default server and client entries. Start's `renderRouterToStream` logs every `onError`, and React Router's default `entry.server.tsx` answers 500 on an `onError` during the shell; neither sees a bail-out for unstarted reads now. A disabled read on a Start or React Router server still rejects (as `QueryDisabledError` did), so those frameworks report it. No `isBrowserRenderError` export: `tooling/rsc-frameworks` doesn't need one.
- **No `QueryProvider`, no `~browserOnly`.** Every framework uses `QueryClientProvider client={…}`. The docs show one `Providers` client component (`"use client"`, takes an optional `client` from a router, otherwise `useState(() => makeQueryClient())`): Start passes the router's client, Next.js and React Router render it bare. `makeQueryClient` lives in a file without a directive, so server components import it too. Files: `www/samples/*/…/providers.tsx`, `examples/nextjs/src/components/app-query-provider.tsx`, `tooling/rsc-frameworks/vite-rsc/providers.tsx`.
- **Hooks under `react-server`.** `index-react-server.ts` exports `useQuery`, `useInfiniteQuery`, `useIsFetching` and `useQueryClient` from `react-server-hooks.ts`, which throw "`useQuery` reads in client components: move this into a file with \"use client\" …". `bindUseQueryClient` works there (it runs at module level in shared files) and returns the throwing `useQueryClient`.
- Tests: `use-query.test.tsx` ("on the server": unmarked server client fetches; under the server `HydrationBoundary` it bails out; disabled reads), `hydration-boundary.test.tsx` (the browser client still fetches under the server boundary), `provider.test.tsx` ("the react-server entry"), `tooling/rsc-frameworks` (an `Author` reading a `waterfallHandle` renders its fallback, its `queryFn` never runs on the server). Checked with temporary probe routes reading a `waterfallHandle` (dev servers, default entries): Start answers 200 with the fallback first and the content streamed into the same HTML, no server logs, no browser exceptions, and the browser makes no request for it; React Router answers 200 with the content in the HTML, no logs or exceptions, and the browser requests `/api/issues/1` once more. Docs: `ssr-and-hydration.md` ("Queries nothing started on the server").
