# Server renders never start requests; one provider everywhere (human)

- **Rule:** on any server client (`client.isServer`), a render never starts a request. Only loaders and server components do. A read with no data, no error and no request in flight (a `waterfallHandle`'s query, a disabled query, one the cache dropped) reads as a thenable that rejects with `BrowserRenderError`; `use()` throws it, React renders the nearest Suspense fallback, and the browser renders the boundary and starts the query. Human: the same setup in every framework. Accepted cost: in TanStack Start a query no loader started no longer renders on the server.
- **One mechanism for disabled and unstarted reads.** `readOf` in `use-query.ts` returns `browserRender(entry)` (`browser-render.ts`) for both; disabled server reads used to reject with `QueryDisabledError`, which Next.js logged. `startIfMissing` returns at once on a server client. The rejected thenable (not a throw from the hook) keeps the bail-out at the boundary above the `use()`, so a component that only passes the thenable down still renders.
- **No `QueryProvider`, no `~browserOnly`.** Every framework uses `QueryClientProvider client={…}`. The docs show one `Providers` client component (`"use client"`, takes an optional `client` from a router, otherwise `useState(() => makeQueryClient())`): Start passes the router's client, Next.js and React Router render it bare. `makeQueryClient` lives in a file without a directive, so server components import it too. Files: `www/samples/*/…/providers.tsx`, `examples/nextjs/src/components/app-query-provider.tsx`, `tooling/rsc-frameworks/vite-rsc/providers.tsx`.
- **Quiet bail-outs per framework.** The error's `digest` is Next.js's `BAILOUT_TO_CLIENT_SIDE_RENDERING`, so Next.js reports nothing on either side. `isBrowserRenderError(error)` (main entry) checks that digest, which survives to the browser's error when the server's `onError` returns it. Checked with a probe route reading a `waterfallHandle`, dev and production builds:
  - TanStack Start: `renderRouterToStream` logs every `onError` (`Error in renderToReadableStream: …`) and returns no digest, and Start has no option for it. `examples/tanstack-start/src/server.ts` is Start's stream handler built from `@tanstack/react-router/ssr/server`'s parts, with an `onError` that returns the digest for bail-outs (bots still wait for `allReady`, through the app's own `isbot`). `src/client.tsx` hydrates with an `onRecoverableError` that skips them. Lost: a `streamHandler` export from `@raf-query/react/tanstack-router` (needs `react-dom/server` and `isbot`, neither a dependency, and a real router render to test); a `console.error` filter (global patch, and the browser still gets no digest).
  - React Router: the default `entry.server.tsx` sets the status to 500 on any `onError` (the bail-out happens during the shell, so the page answers 500) and logs after the shell. `examples/react-router/app/entry.server.tsx` is the default with the bail-out skipped; `entry.client.tsx` skips it in `onRecoverableError`.
  - Without those entries the fallback still renders on the server and the browser still loads the query; only the reports (and React Router's 500) differ.
- **Hooks under `react-server`.** `index-react-server.ts` exports `useQuery`, `useInfiniteQuery`, `useIsFetching` and `useQueryClient` from `react-server-hooks.ts`, which throw "`useQuery` reads in client components: move this into a file with \"use client\" …". `bindUseQueryClient` works there (it runs at module level in shared files) and returns the throwing `useQueryClient`. `load`, the verbs, `HydrationBoundary` and `QueryClientProvider` are unchanged.
- Tests: `use-query.test.tsx` ("on the server"), `provider.test.tsx` ("the react-server entry"), `tooling/rsc-frameworks` (an `Author` reading a `waterfallHandle` renders its fallback, its `queryFn` never runs on the server). Docs: `ssr-and-hydration.md` ("The provider", "Queries nothing started on the server").
